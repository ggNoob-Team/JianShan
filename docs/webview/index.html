角色二维码与会话工作量归属协作计划中P0
最小用户体系只解决“谁在操作、会话属于谁、工作量算给谁”。管理员创建不同工作角色，每个角色有一个稳定二维码；扫码后进入现有 Paseo，不另做一套权限界面。
已确认
  • 管理员创建不同角色二维码；二维码是无限会话入口，保留现有 Paseo 全部功能。
  • 同一角色在手机、电脑、网页看到并操作同一套内容；不同角色也看到同样的全局内容。
  • 二维码只区分“当前操作角色”，本阶段不承担会话隔离或权限隔离。
  • 一个自然人可以有多个工作角色，例如“书记一”“书记二”；系统不需要知道它们属于同一个人。
  • 一个会话同一时间只属于一个角色；新会话自动归当前角色，之后可从 A 转让给 B。
  • 工作量按操作发生时的角色分段统计：转让前算 A，转让后算 B。
  • 现有未归属角色的旧会话暂不处理。
边界
工作角色是二维码身份，与“产品 / 开发 / 测试”职责标签不是同一个概念。二维码泄露后的撤销、设备管理和权限控制留到下一阶段。
验收

设备与环境感知（Device Context）设备计划中P1
服务器和 Agent 必须知道当前是谁、在哪台设备、在哪个界面发起操作，才能判断哪些动作可以在该设备完成。不能把手机、平板、Web、Mac、Windows 和 HarmonyOS 都当成同一个无差别客户端。
至少感知
  • 设备类型、设备 ID、操作系统、客户端版本、在线状态和网络延迟。
  • 当前活动上下文：输入来自手机还是 Mac、当前在工作区 / 输入框 / 终端 / 浏览器 / 设置页，以及当前项目与会话。
  • 输入方式：触屏、硬件键盘、语音、扫码、相机和文件选择器是否可用。
  • 执行能力：浏览器自动化、本地 Codex、终端、文件系统、桌面应用、通知、相机和系统分享等。
用途
Agent 根据设备和当前上下文选择动作：手机负责输入、确认、扫码和查看；Mac / Windows 可以执行本地浏览器、Codex、终端和文件操作；服务器负责统一推理、编排和记录。设备切换时上下文要实时更新。
边界
默认只上报能力与活动元数据，不上报完整屏幕、剪贴板和文件内容；敏感能力需要单独授权。设备状态必须有时效，失联或切后台后不能继续被视为可执行节点。
与分布式 Agent 的关系
这是分布式 Agent 的前置能力：服务器需要先知道哪台设备在线、有什么能力、当前是否适合执行，才能把任务路由到本地 Agent。
分布式 Agent（服务器编排 + 本地执行）Agent计划中P1 · 核心架构部分基础
手机 / 平板只是输入和控制终端，Paseo 与核心 Agent 跑在服务器；但有些自动化必须使用本地电脑上的 Codex、终端、文件和桌面环境。目标是让服务器 Agent 能把指定步骤委派给已配对电脑上的本地 Agent，执行过程和结果回到同一个会话，不再要求用户手动打开电脑上的 Codex。
当前已有基础（2026-11-06）
  • 服务器 daemon 上的 Agent 可调用 browser_* 工具；工具定义与编排在 daemon，模型仍是服务器侧 Agent。
  • 本地 Electron 客户端连接后注册为 browser automation host；daemon 的 broker 把命令发给已连接客户端。
  • browser_new_tab 当前选择“最近注册的浏览器宿主”，后续命令按 browserId 固定回原宿主；新 Tab 和点击都在该客户端的本地 Electron WebView 中执行。
  • 本地浏览器保留本地 Cookie / 登录态；daemon 只传输自动化命令和结果，不传输整屏视频。
  • 这不是本地 Codex：本地客户端承担浏览器执行器，服务器侧 Agent / Codex 负责思考。多客户端并发时也还没有显式“选择在哪台电脑执行”的产品入口。
还需要
明确目标主机、把本地 Codex / 终端 / 文件和桌面动作纳入能力注册，增加逐能力授权、任务确认、超时与断线恢复，形成完整的本地 Agent Worker。
目标形态
以服务器为主、本地为辅：服务器维护主会话、核心推理、任务编排和最终答复；本地 Agent Worker 作为可发现的在线执行节点，向服务器注册自己、当前环境与可用能力。服务器创建 Agent 或分配任务时，能看到本机 Agent 是否在线，并让本地 Agent 执行 Codex、浏览器、终端、文件和桌面自动化；结果回到同一会话。 本地不是另一个大脑，而是服务器 Agent 可以调度的“本地手脚”。
完整模块划分
  • 设备与状态感知：设备类型、系统、客户端版本、在线 / 延迟、当前工作区与会话、输入来源和当前活动界面。
  • 身份、配对与信任：设备稳定身份、公钥、配对、撤销、用户 / 角色权限，以及服务器和本地 Worker 的双向身份校验。
  • 本地 Agent 注册与能力发现：Agent ID、Provider、Codex 能力、工作区、工具目录、负载、心跳和在线状态。
  • 本地 Agent 生命周期：创建、启动、暂停、恢复、停止、重启、查询状态和终止，并定义完整状态机。
  • 目标与短期状态：当前 objective、成功标准、约束、计划、当前步骤、进度、阻塞、待审批、截止时间和 revision；服务器可查询、订阅、修改和取消。
  • 任务路由与调度：按设备能力、在线状态、工作区、权限、负载和用户选择指定执行节点，处理排队、并发和资源锁。
  • 通讯协议：控制面支持注册、启动、目标分配和审批；事件面支持步骤、日志、工具结果、错误、心跳和完成通知；具备请求 ID、幂等、顺序、超时和取消。
  • 上下文与会话同步：服务器保留主会话；本地只接收任务所需上下文并回传执行轨迹、结果和检查点，避免两套割裂记忆。
  • 执行能力与工具目录：本地 Codex、浏览器、终端、文件、Git、桌面应用、MCP / Skills 和系统能力都通过结构化工具暴露。
  • 权限、审批与审计：按设备、工作区、任务和工具授权；读写与危险动作分级确认；本地凭证不离开设备；全程留痕。
  • 故障恢复与离线语义：心跳、重连、任务租约、检查点、幂等、fencing token，明确服务器或本地掉线时任务暂停、继续还是取消。
  • 控制界面：设备与本地 Agent 状态、目标 / 当前步骤 / 阻塞、执行节点选择、暂停 / 取消 / 接管、审批和断线提示。
优先级提升原因
它决定后续办公入口、通用 Agent、本地自动化和多设备协作能不能成立，不再只是远期功能。P1 MVP 先完成“一台服务器 + 一个本地 Agent Worker + 一个本地 Codex + 目标状态回传”的闭环；多设备调度、离线自治和跨设备迁移后置。
典型场景
用户在平板上提出“自动申请飞书 API key”。服务器 Agent 负责理解任务、编排步骤和保持会话；其中需要在本机 Codex / 浏览器 / 本地凭证完成的部分，自动交给指定电脑执行，并把确认、日志和结果实时回传。
运行模型
  • 服务器为主：负责核心推理、任务分解、主会话、上下文、路由和最终答复。
  • 本地为辅：本地 Agent Worker 负责执行只能在本机完成的工具调用与命令，并把结果交回服务器。
  • 两者通过同一任务 ID、会话 ID 和工具调用 ID 关联；用户只看到一条连续会话。
  • 一个用户可以配对多台电脑，由服务器根据能力、在线状态或用户选择指定执行节点。
  • 服务器必须通过「设备与环境感知」知道本地 Agent 的在线状态、工具能力、当前工作区和适合执行的动作。
通讯建议
  • 优先复用现有 connected-host、routed session 和 relay / E2E 通道；本地节点主动向服务器或 relay 建立持久连接，避免要求公网入站端口。
  • 本地节点注册 hostId、工作区、可用 Agent / 工具、版本和心跳；服务器维护在线状态与能力表。
  • 服务器下发带幂等键的任务请求：目标节点、工作区、工具、参数、超时和权限范围；本地持续回传 progress、stdout / stderr、确认请求和最终结果。
  • 断线后任务进入可恢复状态；重连时按序号补发结果，不能因为网络抖动重复执行写操作。
安全边界
本地凭证不离开本机；命令限制在授权工作区；写文件、安装、部署、读取敏感信息和对外提交必须确认； 服务器不能因为能下发任务就获得电脑的无限权限。
MVP 验收
服务器上的 Agent 能把一个明确任务委派给一台在线电脑，由本地 Codex 执行，手机端实时看到执行状态并收到结果； 支持取消、超时、失联恢复和危险操作确认。
开放问题
主会话最终存在服务器还是本地；本地执行者是 Paseo Agent、Codex 子进程还是两者组合；多台电脑如何选择； 离线任务是否排队；服务器与本地之间哪些内容需要端到端加密。
消息系统（持久化消息中心）消息计划中P1部分基础
要做的不是一个临时聊天记录，而是全系统统一、可持久化、可检索、可追踪的消息层。人、Agent、系统任务和定时任务都可以产生消息，并能在手机、网页和电脑之间同步。
范围
  • 统一消息实体：发送者、接收者、所属会话 / 频道、来源、正文、附件、时间和上下文链接。
  • 支持异步投递、离线消息、跨设备同步、未读状态、通知、搜索和归档。
  • 消息可以关联 Agent 会话、任务、笔记、文件和分布式 Agent 执行结果。
  • 消息写入需要幂等和去重；失败可重试，敏感内容需要有保存和清理策略。
与实时聊天关系
消息系统是底层事实来源和持久化记录；实时聊天系统是建立在它之上的低延迟交互体验。两者都要做，但不做两套重复数据模型。
开放问题
消息保留多久；是否支持编辑与撤回；系统事件是否全部进入消息中心；敏感消息是否默认本地保存。
实时聊天系统消息计划中P1部分基础
面向人、Agent 和团队工作流的实时双向聊天。消息应低延迟到达，支持流式输出、在线状态、输入状态、投递确认和多端同步；现有 Agent 会话和 WebSocket 只能算局部基础，不是完整聊天系统。
范围
  • 一对一和群组聊天；人和 Agent 可以出现在同一个会话中。
  • 实时消息、流式回复、在线 / 离线、正在输入、已送达 / 已读状态。
  • 断线重连后补消息、保持顺序、去重和幂等，避免重复发送或丢失。
  • 消息可与任务、笔记、会话和本地执行过程互相跳转。
  • 先支持文字、语音转写、文件和链接；音视频通话不纳入第一版。
验收
手机、电脑和网页在同一个聊天中看到一致顺序；断网恢复不丢消息；Agent 流式回答可中断、可继续；消息发送失败有明确重试状态。
开放问题
群聊中的 Agent 如何被点名和分配任务；是否支持多个 Agent 同时回复；聊天和 Agent 会话是同一模型还是两种模型。
